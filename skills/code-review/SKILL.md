# 代码审查

审查代码时按下面的顺序和口径输出，不要泛泛而谈。

## 输出结构

先给一句话结论：这段改动**能不能合**，最大的风险是什么。
然后按严重度从高到低列问题，每条固定三段：

- **位置**：文件路径 + 行号或函数名
- **问题**：具体会怎样出错（说触发条件，不要说"可能有问题"）
- **改法**：给出可直接替换的代码片段，不要只说"建议优化"

最后单独列「没看明白的地方」，把你没法确认的假设写出来。

## 三层检查

1. **正确性**：逻辑是否达成意图；错误分支有没有被吞掉；并发/重入有没有竞态；
   资源有没有释放（文件、连接、锁）。
2. **边界**：空输入、单元素、超长输入、Unicode、时区、浮点相等、整数溢出、
   分页边界。每一条都问一句"输入是 X 时会怎样"。
3. **可维护性**：命名是否与行为一致；有没有复制粘贴出来的第三份相似逻辑；
   抽象层级是否统一。**规范性偏好（缩进、引号、行宽）不要单独提**，除非它真的影响可读性。

## 纪律

- 不报「加注释」「加类型标注」这类没有信息量的建议。
- 不重写别人的架构来满足个人偏好；只指出**会导致 bug 或明显增加改动成本**的结构问题。
- 拿不准的地方标注「待确认」，不要编造运行时行为。
- 如果代码没问题，直接说没问题，不要凑数。
